# M1：会话回放器设计

2026-11-02 · @PM · 依据：`docs/PLAN.md` v2.1、`docs/m1_agentx_data.md`

**一句话：** 回放器分成离线和在线两部分。离线部分把 AgentX trace 确定性地转换成一份"负载文件"，每个请求的 token、长度、间隔、hint 都提前算好；在线部分读取负载文件，以闭环方式向 vLLM 发送请求并逐请求记录指标。同一份负载文件可以对任何策略重复回放，保证各策略看到逐 token 相同的请求序列。

## 1. 目标与范围

**要做到：**

- 复现 AgentX 根会话内的前缀共享结构（包括上下文切换和子 Agent 分叉）
- 复现链内"请求返回后、下一请求发出前"的间隔，并在间隔期间产生真实的并发干扰
- 负载与模型输出无关、与策略无关，可以完全复现
- 随请求携带 `agentkv.tool_gap` hint，并能切换 hint 来源
- 逐请求记录客户端延迟，并能与服务端埋点关联

**不做：**

- 不还原原始文本、编码任务语义或模型输出质量
- 不还原工具名和逐工具耗时（数据里没有）
- 不还原链之间精确的派生和合流依赖

## 2. 设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| token 来源 | 由哈希确定性合成为主；回填实际输出为可选模式 | 负载与模型输出无关，各策略逐 token 相同；回填模式只用来量化差异 |
| 缩放 | 按根会话比例，32K 上下文预算 | 输入中位数约 10.6K，比全局比例（约 4.6K）更接近真实压力 |
| 间隔 | 先截断上限，再乘压缩系数，两者都是参数 | 原始长尾达到天级；对驱逐而言关键是间隔期间的其他流量 |
| 负载子集 | 固定种子抽样 N 个根会话 | 可复现；关键实验换 2 到 3 个种子重复 |
| 并发控制 | 根会话按泊松过程到达 | 最接近真实服务，到达速率是 E2 的自变量 |
| 结束条件 | 固定时长，丢弃预热段和收尾段 | 各策略时长一致，只统计稳态 |
| 输出长度 | `max_tokens` 取缩放后的输出长度，开启 `ignore_eos` | 输出长度与 trace 严格一致，不受合成 prompt 影响 |
| hint 携带 | 每个请求都带"本请求结束后的间隔"，链内最后一个请求带 `final=true` | 策略在请求结束时开始计时；单次调用的辅助链也带 hint |

## 3. 整体流程

```
traces.jsonl ──► [离线] 构建负载文件 ──► workload.parquet + manifest.json
                     │
                     ├─ 1. 抽样根会话（seed, N）
                     ├─ 2. 拆链（复用审计中的 detect_agent_chains 结果）
                     ├─ 3. 计算每个根会话的缩放比例 α
                     ├─ 4. 由 hash_ids 合成 token
                     ├─ 5. 计算间隔（截断、压缩）、事件锚点和各档 hint
                     └─ 6. 写出负载文件和校验值

workload.parquet ──► [在线] 回放 ──► requests.parquet（每请求一行）
                     │
                     ├─ 根会话按泊松过程到达
                     ├─ 链等待锚点请求完成后延迟启动，链内闭环
                     └─ 固定时长，记录稳态窗口
```

离线和在线分开的好处：负载文件生成一次就固定下来，换策略时只重跑在线部分；负载文件的 SHA256 写进每次实验的记录，可以直接证明不同策略用的是同一份负载。

## 4. 离线部分：构建负载文件

### 4.1 抽样

- 从 393 个根会话中用固定种子抽取 N 个，抽样单位是根会话，其下所有子 Agent 和推断链一起保留
- 抽样参数（种子、N、过滤条件）写进 `manifest.json`

### 4.2 缩放

对每个根会话 r：

```text
α_r = min(1, 32512 / max_{请求 ∈ r}(in + out))
in'  = floor(α_r × in)
out' = ceil(α_r × out)
第 k 个哈希块在缩放后的起止位置：[q(k), q(k+1))，其中 q(k) = floor(α_r × 64 × k)
```

同一根会话及其全部子 Agent 共用 α_r，这样根会话内的前缀树在缩放后保持一致。

### 4.3 合成 token

对根会话 r 中出现在位置 k 的哈希块 h：

1. 种子 = `SHA256(root_id ‖ hash_id)` 的前 8 字节
2. 用该种子初始化 `numpy.random.Generator(PCG64)`，生成 `q(k+1) − q(k)` 个 token
3. token 从模型词表中采样，排除特殊 token（BOS、EOS、padding 等）

一个请求的 prompt 就是其 `hash_ids` 依次对应的 token 段拼接。因为相同的哈希一定生成相同的 token，trace 中两个请求共享多少个块，合成后就共享对应的 token 前缀。

**需要验证的假设：** 同一根会话内，同一个 `hash_id` 总出现在同一位置 k。如果 trace 中存在同一哈希出现在不同位置的情况，块长度会对不上。离线阶段要扫描检查，有违反就报错，并改为固定块长（`ceil(α_r × 64)`）的退化方案。

请求通过 `/v1/completions` 以 token ID 列表的形式发送，不经过 chat template，避免模板引入额外 token。

### 4.4 间隔

对推断链中相邻的请求 k 和 k+1：

```text
gap_k        = t_{k+1} − (t_k + api_time_k)        # trace 中的观察间隔
gap'_k       = min(gap_k, G_cap) × c               # 截断后压缩
```

链启动采用事件锚定：锚点 A = 同一根会话中，结束时间 ≤ 链 C 首请求 t 的请求里结束时间最晚的一个（不属于链 C）；启动延迟 = min(t_C − end_A, G_cap) × c；无锚点时以根会话到达为锚，延迟 = min(t_C, G_cap) × c。

锚点依据原始 trace 的 `end_A = t_A + api_time_A` 选择，可以是另一条链的任意请求。在线等待该请求在本次回放中实际完成，再等待启动延迟；两个子 Agent 可以锚定同一父请求并行启动。链首保存 `anchor_trace_req_idx` 和 `start_delay_s`；无请求锚点时前者为空，但后者仍有值，后续轮次两列均为空。

结束时间并列时，按 `(end, t, chain_turn, chain_id, trace_req_idx)` 取最大值。为处理同刻零耗时请求，定义严格事件顺序 `(t, chain_turn, chain_id, trace_req_idx)`，锚点必须在该顺序中早于链首；链内前驱也按此顺序在前，依赖图因此无环。正耗时请求只需满足原始结束时间条件。

链内最后一个请求没有 gap，标记 `final=true`。`chain_offset_s` 保留为**仅供参考，在线调度不使用**：仍按根会话活跃区间合并、截短相邻合并区间间的长空闲后映射链首时间，再乘 c。该参考映射保持零点和首个活跃区间之前的延迟。`chain_offset_orig_s` 保存链首未经处理的原始 `t`。这两列不决定事件锚定回放的发送时刻。

截断比例（有多少间隔被截断）写进 `manifest.json`，报告中要引用。

### 4.5 hint

每个请求预先算好四档 hint 值，在线回放时按参数选择其中一档：

| 档位 | `expected_gap_ms` | 说明 |
| --- | --- | --- |
| `none` | 不携带 hint | 无 hint 基线 |
| `perfect` | `gap'_k` | 上界 |
| `noisy` | `gap'_k × u`，u 在 [0.5, 2] 上按对数均匀分布，种子固定 | 鲁棒性 |
| `online` | 同一链内此前已发生的 `gap'` 的指数滑动平均；链的第一个请求使用未被抽中根会话的链内间隔中位数 | 现实中可实现的预测（M7） |

`gap_p90_ms` 在 `online` 档取同一链历史间隔的 P90，其他档取 `expected_gap_ms × 2`。

在线 hint 的先验仅使用未被抽中的根会话，取其中所有链内间隔经 `min(gap, G_cap) × c` 处理后的中位数；不读取被抽中根会话的未来间隔。无链内历史时，EMA 与 P90 均使用该先验；第一条实际历史间隔初始化 EMA，后续默认 EMA 系数为 0.5。`manifest.json` 记录先验值（秒）、参与计算的间隔数、未抽中根会话 ID 和数量及审计来源校验值。若无可用的未抽中链内间隔则拒绝生成。

hint 以官方信封格式放在 `kv_transfer_params.kv_hints` 中：

```json
{
  "kv_transfer_params": {
    "kv_hints": {
      "protocol_version": 1,
      "message_id": "<root_id>/<chain_id>/<chain_turn>",
      "actions": [{
        "action_id": "gap-0",
        "action_type": "agentkv.tool_gap",
        "action_version": 1,
        "payload": {
          "session_id": "<root_id>/<chain_id>",
          "turn": 3,
          "parent_session": "<root_id>",
          "tool_name": null,
          "expected_gap_ms": 1200,
          "gap_p90_ms": 2400,
          "final": false
        }
      }]
    }
  }
}
```

字段名在 M4 中向 #62382 对齐后可能调整，负载文件保存原始数值，信封在在线阶段才组装，改字段名不需要重建负载文件。

### 4.6 负载文件格式

`workload.parquet`，每个请求一行：

| 字段 | 含义 |
| --- | --- |
| `root_id`、`chain_id`、`chain_turn` | trace 中的根会话、推断链、链内序号 |
| `trace_req_idx` | 在原始 JSONL 中的位置，便于回查 |
| `is_subagent`、`is_aux` | 是否属于显式子 Agent；是否为单次调用的辅助链 |
| `chain_offset_s` | 压缩后的绝对偏移，仅供参考，在线调度不使用；只在链首请求上有效 |
| `chain_offset_orig_s` | 链首请求的原始 `t`（秒，未截断、未乘 c），只在链首请求上有效 |
| `anchor_trace_req_idx` | 链首的请求锚点；无请求锚点时为空，表示根会话到达；后续轮次为空 |
| `start_delay_s` | 锚点完成后到链启动的延迟（秒）；无请求锚点时从根会话到达计时；后续轮次为空 |
| `prompt_token_ids` | 合成的 token 列表 |
| `prompt_len`、`max_tokens` | 缩放后的输入长度、输出长度（原输出为 0 时设为 1，并标记 `out_zero_orig`） |
| `lcp_prev_tokens` | 与链内上一请求的预期共享前缀长度（缩放后） |
| `gap_after_s` | 本请求结束后到下一请求发出的间隔，`final` 时为空 |
| `gap_truncated` | 是否被截断 |
| `hint_perfect_ms`、`hint_noisy_ms`、`hint_online_ms`、`hint_online_p90_ms` | 各档 hint 值 |
| `final` | 是否为链内最后一个请求 |

`manifest.json` 记录：trace 的 revision 和 SHA256、抽样参数、缩放预算、`G_cap`、`c`、噪声种子、词表与模型名、各项统计（请求数、截断比例、长度分布），以及 `workload.parquet` 的 SHA256。

`schedule_estimate.parquet` 是单独的小文件，不修改 `workload.parquet` 或已有字段。固定假设每个请求服务时间 s=0.5 秒，按事件锚点和链内间隔计算预计调度；每行对应一个请求，以 `root_id`、`chain_id`、`chain_turn`、`trace_req_idx` 关联原负载，新增 `est_send_s`（相对根会话到达的预计发送时间）和 `est_duration_s`（根内所有请求的最大预计完成时间，同根各行重复该值）。两列单位均为秒；服务时间、源负载 SHA256 和估算器代码 SHA256 写入文件元数据。该文件不含 token 列，也不改变原来的三档服务时间估算结果。

## 5. 在线部分：回放

### 5.1 调度模型

基于 `asyncio`，HTTP 客户端使用流式请求以测量 TTFT。

1. **根会话到达**：按到达速率 λ 生成泊松到达时刻，每次从抽样集合中均匀、有放回地抽取根会话，创建进度 τ=0 的独立实例；初始已进行实例按第 5.5 节抽取。CLI 的 λ 单位为根会话/分钟，计算时换为根会话/秒
2. **链启动**：链在 `anchor_trace_req_idx` 指定的锚点请求完成后，等待 `start_delay_s` 再启动；无请求锚点时从根会话到达开始等待。`chain_offset_s` 仅供参考，在线调度不使用。根会话到达时为全部请求预建完成事件，按 `(根会话实例 ID, trace_req_idx)` 定位，避免链的文件顺序或根会话循环复用影响依赖
3. **链内闭环**：发送请求 k → 收到最后一个 token → 等待 `gap_after_s` → 发送请求 k+1；`final` 后链结束
4. **安全阀**：设置最大在途请求数；达到上限时新请求排队，并记录排队次数和时长。正式实验中安全阀不应被触发，触发则说明负载设置过重

### 5.2 时间窗口

- 总时长 T，前 W_warm 为预热段，最后 W_cool 为收尾段
- 到达 T 时停止发送新请求，等待在途请求完成（设超时上限）
- **统计范围**：发送时刻落在 `[W_warm, T − W_cool]` 内且 `is_entry=false` 的请求；另外报告窗口内全部请求数和 is_entry 数量、占比
- 窗口参数写进每次运行的记录

### 5.3 hint 发送

- 按 `--hint-tier` 选择档位，在发送时组装信封
- 回放器计数"发出的带 hint 请求数"，与策略侧计数"收到的有效 hint 数"在运行结束后核对，两者必须相等

### 5.4 请求 ID

每个请求设置可追溯的请求 ID（以所用 vLLM 版本支持的方式，如请求头或请求体字段），格式为 `<run_id>/<root_id>#<i>/<chain_id>/<chain_turn>`，用于和服务端 M0 埋点、per-request metrics 关联。i 是会话实例编号，见第 5.5 节。

### 5.5 稳态初始化

**目的：** 实验窗口如果从空状态开始，所有会话都从第一个请求回放，30 到 40 分钟内长会话只能跑完开头，而长会话的后期恰好是上下文最长、前缀复用最多的部分。稳态初始化让窗口一开始就包含一批处在不同进度的会话，使窗口内发出的请求在分布上等同于长期稳定运行的服务。

#### 5.5.1 记号

依据 `schedule_estimate.parquet`（固定服务时间 s = 0.5 秒的估算调度），对每个请求 r 有：

- `est_send(r)`：预计发送时刻，相对根会话到达
- `est_end(r) = est_send(r) + s`

对每个根会话 R 有预计时长 `D_R = max_{r∈R} est_end(r)`。

每个请求有唯一的**触发事件** `trigger(r)`：

| 请求 r 的位置 | trigger(r) |
| --- | --- |
| 链内非首请求 | 同链的上一个请求 |
| 链首，且 `anchor_trace_req_idx` 非空 | 锚点请求 |
| 链首，且 `anchor_trace_req_idx` 为空 | 根会话到达 |

#### 5.5.2 会话实例

一次实验中，回放的基本单位是**会话实例**：一个根会话 R、一个实例编号 i、一个进度点 τ（秒）。同一个根会话可以在一次实验中出现多次，每次都是独立实例。

**实例的 token 变换：** 每个实例使用一个词表置换 `π_{R,i}`，作用在该实例所有请求的每个 token 上。置换在合法词表（排除特殊 token 后的 151,655 个 ID）上进行，种子为 `SHA256(UTF8(root_id + "#" + 十进制 i))` 的前 8 字节（大端）。

- 置换是一一映射，与位置无关，所以实例内部任意两个请求的最长公共前缀保持不变
- 不同实例之间的 token 序列在第一个位置就几乎必然不同（概率约 `1 − 1/151655`），不会产生跨实例的前缀命中
- 变换在在线阶段进行，`workload.parquet` 及其 SHA256 不变
- 请求 ID 格式改为 `<run_id>/<root_id>#<i>/<chain_id>/<chain_turn>`

这一规则同时解决了第 11 节待定问题 2（根会话复用）。

#### 5.5.3 实例从哪里来

设到达速率为 λ（根会话/秒），抽样集合中根会话预计时长的平均值为 `E[D] = mean_R(D_R)`。

**初始实例（t = 0 时已在进行）：**

1. 数量 `M₀ ~ Poisson(λ × E[D])`，用固定种子抽取，实际值写进 `run.json`
2. 每个初始实例独立地按**与 D_R 成正比的概率、有放回地**抽取根会话
3. 每个初始实例的进度点 `τ ~ Uniform(0, D_R)`，独立抽取

**新到达实例：**

1. 从 t = 0 开始按速率 λ 的泊松过程到达
2. 每个新实例**均匀、有放回地**从抽样集合中抽取根会话（替代第 5.1 节原来的“按固定顺序取，用完循环”）
3. 进度点 τ = 0，即从头回放

依据：根会话按泊松过程到达、各自持续 D_R，属于 M/G/∞ 系统。稳态下任意时刻正在进行的会话数服从均值为 λ × E[D] 的泊松分布，每个会话被抽中的概率与时长成正比，进度点在 `[0, D_R]` 上均匀分布。

全部随机抽取（M₀、初始根会话、τ、到达时刻、新实例的根会话）使用同一个 `--population-seed` 派生的独立随机流，同一参数下完全可复现，并且与策略无关。

#### 5.5.4 实例从 τ 开始回放的规则

对实例 (R, i, τ) 中的每个请求 r：

1. **不回放**：`est_send(r) < τ` 的请求，视为在 τ 之前已经发出
2. **回放**：`est_send(r) ≥ τ` 的请求。它的发送时机由 trigger(r) 是否被回放决定：

| trigger(r) | 发送时机 |
| --- | --- |
| 是一个被回放的请求 | **事件驱动**：照常执行，链内为 trigger 实际完成后等待 `gap_after_s`；链首为锚点实际完成后等待 `start_delay_s` |
| 是一个未被回放的请求，或是根会话到达 | **定时触发**：在实例开始后 `est_send(r) − τ` 秒发送 |

这条规则统一覆盖了各种情况：

- **τ 落在某个请求执行期间**（`est_send(r_j) < τ < est_end(r_j)`）：r_j 不回放，视为已经发出、将在 `est_end(r_j)` 完成。同链下一个请求 r_{j+1} 按定时触发，在 `est_send(r_{j+1}) − τ = (est_end(r_j) − τ) + gap_after_s(r_j)` 秒后发送。以 r_j 为锚点、在 τ 之后启动的链同理
- **τ 落在链内两个请求的间隔中**：下一个请求按定时触发，剩余等待时间为 `est_send(r_{j+1}) − τ`
- **链在 τ 之前已经结束**：链内全部请求都不回放，整条链跳过
- **链在 τ 之后才启动，锚点在 τ 之前已发出**：链首按定时触发
- **链在 τ 之后才启动，锚点也在 τ 之后**：锚点被回放，链首照常事件驱动
- **以根会话到达为锚点的链**：始终定时触发。τ = 0 时延迟为 `est_send(r) = start_delay_s`，与正常回放一致
- **τ ≥ D_R**：没有请求被回放，实例为空（初始实例按 τ < D_R 抽取，不会出现）

**一致性要求：** τ = 0 时，按本规则得到的回放与第 5.1 节的正常回放完全一致。

#### 5.5.5 is_entry 的定义

一个被回放的请求 r，当且仅当 **trigger(r) 是一个未被回放的请求** 时，标记 `is_entry = true`。

含义：r 的前文（上一轮、或父请求所在的上下文）在本实例中从未被发送过，缓存里不可能有，r 必然冷启动。这是初始化带来的人为冷启动，不是真实负载的特征。

- 新到达实例（τ = 0）中没有 is_entry 请求
- 以根会话到达为锚点的链首不算 is_entry，它们的冷启动是真实会话开头本来就有的
- is_entry 请求照常发送，因为它要把前缀加载进缓存，后续请求才能命中。只是**不计入统计**
- 每次运行报告 is_entry 请求数及其占窗口内请求的比例

#### 5.5.6 统计窗口

- 总时长 T，预热 W_warm，收尾 W_cool；统计发送时刻落在 `[W_warm, T − W_cool]` 内、且 `is_entry = false` 的请求
- 窗口参数、M₀、各实例的 (R, i, τ) 写进 `run.json`

`requests.parquet` 每个实际发送的 HTTP 请求一行，保留原负载字段；其中 `prompt_token_ids` 为原负载的 token，实例变换后的实际发送内容通过置换种子和 `sent_prompt_sha256` 追溯。未发送的初始历史、截止时间后的请求及失败依赖分支不算成失败 HTTP 请求；因安全阀等待到截止仍未发送的项及被阻断的依赖数量在 `run.json` 单独记录。请求不自动重试，失败请求阻断依赖于其完成的请求，其他定时分支继续。T 时停止新发送，已发送请求在排空超时内完成。

计时使用返回 token ID 的首个非空增量（不支持 ID 时退回非空文本）；TPOT 按首末 token 时间除以输出间隔数计算。服务端轻量观测插件记录逐请求名义 GPU、外部 CPU 及重算来源，必须满足三者之和等于 prompt_len；未采集到的有效口径及 replay_overlap 保持为空，不以名义值代替。`metrics.jsonl` 定期记录服务端运行和等待队列数量，供试跑负载判断。

为控制调度长尾，token 列在计时前解码为 Arrow 缓冲区，请求体在触发时立即交给两个专用构建线程，预留整个等待间隔。发送截止点只发送字节；零等待或构建超时仍照实记录迟发，不移动计划时刻。实例置换的稠密查表与原词表置换逐 token 等价。另以 10ms 绝对周期采样事件循环实际唤醒相对计划的延迟，写入 `loop_lag.parquet`；延迟跨过周期时记录 `missed_checks`，`run.json` 保存分位数和总漏检数。

## 7. 验证

### 7.1 离线（不需要 GPU）

1. **确定性**：同样的参数生成两次，`workload.parquet` 的 SHA256 相同
2. **位置唯一性**：每个根会话内，同一 `hash_id` 只出现在同一位置
3. **LCP 一致性**：对每条链内的相邻请求，以及随机抽取的同根会话请求对，合成 token 的最长公共前缀等于 `q(trace 块级 LCP)`
4. **预算**：每个请求 `prompt_len + max_tokens ≤ 32512`
5. **间隔**：`gap_after_s` 非负；截断比例与 manifest 一致

补充检查事件锚点的同根、跨链、原始结束时间条件和最晚完成选择，验证依赖图无环、无锚点时的根到达延迟，以及两条子 Agent 链能共享父请求锚点并行启动。

离线估算回放时长时，假设每个请求的服务时间固定为 s（分别取 0.2、0.5、1.0 秒），每根会话独立以到达时刻为零点，沿依赖图计算：链首发送时间为锚点回放完成时间加 `start_delay_s`（无锚点则为 `start_delay_s`），链内后续发送时间为前一请求回放完成时间加 `gap_after_s`，完成时间为发送时间加 s。根完成时间取该根所有请求完成时间的最大值。报告根完成时间的中位数、P90、最大值，以及发送时间 ≤1500 秒的请求数占全部请求数的比例。估算允许无限并发，不包含服务端排队、网络开销或安全阀限制，也不在 25 分钟截断根完成时间。

### 7.2 在线（需要 GPU）

1. **对齐 hello world**：构造一个小 trace，结构与 hello world 相同（一条两轮链 + 若干干扰请求），回放结果中 GPU 和 CPU 命中、重算数与手动脚本一致。由于使用合成 token，上一轮输出部分的预期差异要在对照中说明
2. **单链无干扰**：只回放一条链，GPU 命中应接近 `lcp_prev_tokens`，差值只来自最近一轮输出位置和块对齐
3. **hint 核对**：发出数等于收到数
4. **调度误差**：`gap_actual_s − gap_after_s` 的 P99 在几十毫秒以内
5. **回填模式对照**：同一小子集分别用合成模式和回填模式运行，记录 GPU 命中差异

### 7.3 稳态初始化的验证（离线）

`agentkv/bench/steady_state.py` 的单元测试：

1. **τ = 0 一致性**：入口列表与正常从头回放完全一致，没有 is_entry
2. **τ 落在请求执行期间**：该请求不回放；同链下一个请求定时触发，延迟 `= est_end − τ + gap_after_s`，且为 is_entry
3. **τ 落在间隔中间**：下一个请求定时触发，延迟 `= est_send − τ`，且为 is_entry
4. **链在 τ 之后启动、锚点在 τ 之前**：链首定时触发，为 is_entry
5. **链在 τ 之后启动、锚点在 τ 之后**：链首事件驱动，不是 is_entry
6. **以根会话到达为锚点的链**：定时触发，不是 is_entry
7. **τ ≥ D_R**：实例为空
8. **置换**：同一实例内任意两个请求的 LCP 在置换前后相同；两个不同实例的同一请求从第一个 token 起不同

### 7.4 λ 的离线估算实验

不需要 GPU，用估算调度（s = 0.5 秒）、无限并发进行事件模拟。

**参数：** T = 40 分钟，W_warm = 10 分钟，W_cool = 0；λ ∈ {0.5, 1, 2, 4} 个根会话/分钟；`--population-seed` 固定。每个 λ 跑两种：开启稳态初始化、关闭稳态初始化（M₀ = 0），后者作为对照。

### 7.5 离线容量与调度长尾验证

`agentkv/bench/capacity.py` 基于 v3 及同根、同种子的 16K 重新合成负载，计算严格更早发送请求的最大 LCP，按 token 加权得到无限缓存上限。以稳态长期到达率计算所需 prefill 曲线，不把有限窗口抽样噪声当成长期到达负载；固定 s=0.5 的有限槽位模拟与满槽位 KV 抽样分别报告，GPU 采用二者较大的 P90 保守定容。筛选要求 `2.5×运行中KV P90 ≤ GPU池 < CPU层 ≤ 0.8×工作集`，且 `1.5 ≤ CPU层/GPU池 ≤ 2`。工作集是活跃链最近 prompt 的不同前缀之并（实例间不共享，排除输出），在 s=0.5 的稳态人口估算中每 10 秒采样，用统计窗口 P50 作上述约束的基准；报告同时列 P90。原先的 GPU+CPU<工作集约束取消，未通过配置记录具体缺口。模型假设和全部指纹写入容量 `run.json`。

`agentkv/sim/two_tier.py` 是 CPU-only 最小缓存模拟器：完整 16-token 前缀块、GPU/CPU 独立 LRU、完成时重复写 prompt 的 CPU 镜像，GPU 淘汰不插入 CPU；GPU 在途 KV 钉住、输出作私有占用，完成后才使新块可复用。GPU 连续前缀后用 CPU 连续前缀延伸，其余全部重算。服务固定 s=0.5，搬运零耗时；稳态初始化只生成请求入口，不预填缓存，is_entry 不计入统计。同人口无限缓存对照用于区分块边界、冷启动和驱逐损失。单链无限缓存须等于最大 LCP 上限（token 粒度）；CPU 小于 GPU 的循环工作集测试须几乎没有额外 CPU 命中。

GPU 试跑推荐门槛为：模拟 LRU 命中率相对全负载理论上限及同人口无限缓存对照均至少低 10 个百分点（对“明显低于”的操作定义），且由 token 加权重算比例推得的 prefill 需求不超过 `22000×70%=15400 token/s`；同时列出 34k 算力线占比。只过容量约束的配置不自动推荐，模拟也不保证共享 GPU 稳定。

`agentkv/bench/scheduler_probe.py` 固定 125 条链、12K prompt、4 秒假服务时间、0.3 秒链内间隔、6 轮，使用独立假服务进程。prompt 从 v3 不同行组抽取，冻结归档调度器及归档置换代码作为修复前基线。每个版本每次 750 请求，保留请求体构建、10ms 事件循环延迟和间隔误差，要求修复后链内间隔绝对误差 P99<50ms；失败或中间版本保留，不通过改变负载绕过。此探针验证客户端调度，不代替独占 GPU 的容量验收。

### 7.6 稳定性判据（后续运行统一使用）

统计窗口为 `[W_warm, T−W_cool]`。以下条件同时满足才判为稳定；不再使用首末五分钟队列均值比值或无条件的运行并发接近槽位上限。

1. 等待队列为0的有效采样占比≥80%，且队列P99≤`max_num_seqs`。采样等权，分位数用线性插值；缺失指标不当成0。
2. 将等待队列长度对实际采样时间（秒）做含截距的普通最小二乘回归，斜率×1800秒严格小于1，即30分钟拟合增量<1；负斜率直接满足。报告斜率、拟合增量和采样数。
3. 成功、非is_entry请求按发送时刻分到统计窗口前后两半，后半段TTFT中位数/前半段中位数≤1.5。任一半无有效请求时无法判定，不得默认稳定。
4. 仅在存在KV阻塞证据时检查GPU池：等待队列>0且有未开始请求因KV分配不足无法开始，则该事件时运行数应接近`max_num_seqs`。操作定义为≥`max_num_seqs−1`（最多差1个槽位）；否则记录GPU池偏小、该条件失败。普通槽位排队、异步CPU回载等待不等同KV不足。须用服务端分配失败事件与同时的队列/运行数判断；无KV阻塞时不要求持续占满槽位。

缺少必要观测记为无法判定，不能列入稳定曲线。失败/不稳定/无法判定的运行逐次列出并保留全部产物，不删除、不换种子绕过。稳定判据版本、数值、是否有KV阻塞及每项结论写入每次分析结果。

### 7.8 E0 重算来源分解

对统计窗口内每个成功、非 `is_entry`、有完整名义缓存计数的请求 r，按同实例实际发送顺序计算前缀；“之前”是严格更早发送，不要求已经完成，同一时刻发送的请求互不计入历史。被初始化跳过的请求不属于历史，已经发送的 is_entry 请求属于历史。实例之间不共享前缀。

所有参与分类的长度均向下取整到16-token整块。记 `L=floor(prompt_len/16)×16`，`hit=floor((GPU命中+CPU命中)/16)×16`；u 是 r 与同实例此前任意已发送请求的最大 LCP；p 是 r 与触发请求的 LCP。触发请求统一为链内上一请求或链首锚点请求；以根会话到达为触发时 p=0。

| 重算类别 | token数 |
|---|---|
| 不可避免 | L−u |
| 间隙期间（含排队）的驱逐 | max(0,p−hit) |
| 其他驱逐 | max(0,u−max(p,hit)) |

正常时 hit≤u，三类之和为 L−hit。若 hit>u，将 u 提高到 hit 后分解，并记录异常数，报告中逐次列出；正常预期为0。原始 `prompt_len−L` 尾块另外报告，不混入整块曲线。原始名义命中/重算统计仍保留，不能静默用舍入后的值替代。

第二类的区间是触发请求完成至当前请求开始调度，包含请求外间隙、客户端调度误差、客户端安全阀及服务端排队。报告这类请求的平均排队时长（客户端安全阀等待加服务端EngineCore接收到首次调度的等待），并列出可观测请求数；不能把缺失等待观测当成0。服务端首次调度前的异步回载等待也计在该口径内。

模拟器额外记录每个块最后从GPU、CPU两层都消失的时刻。对每个计入第二类的整块，核验该时刻落在 `[触发请求完成, 当前请求开始调度]` 内（浮点容差1ns），要求一致率100%；失败先停止、调查，不启动正式GPU矩阵或继续生成结论。无限缓存的单链测试要求两类驱逐均为0；两轮之间的干扰请求测试要求共享前缀的损失全部归入第二类。真实运行按前缀来源分类，不要求逐块驱逐记录。

口径边界：u依据发送历史，可能包含尚未完成、尚未生成的并发前缀；“其他驱逐”按上述剩余未命中公式统计，不单独证明物理驱逐。无限缓存零驱逐测试采用串行闭环链。名义计数保留服务端整块和末token回放的实现边界；对齐后的重算与原始名义重算满足 `原始重算 = 整块分类之和 + prompt尾部token − 命中计数的尾部token`，两个尾部量均单列复核，不能假设全部prompt尾部均重算。

各次真实运行与同人口LRU/Oracle模型分别统计，不要求固定0.5秒模型与真实服务时间形成相同请求序列。逐次记录人口指纹、输入SHA256、提交号、分类版本和异常计数。仅稳定真实运行进入λ曲线；其同人口模拟及Oracle也仅使用对应稳定运行，报告各λ保留的种子数。失败、不稳定或无法判定的运行单列，不能删去或换人口。

复核入口为 `python -m agentkv.analysis.finalize_e0 --run-dir <完成的临时目录>`：独立重算队列回归、分位数和TTFT判据，核验人口及文件指纹，生成稳定人口汇总图和全部人口的队列诊断。`requests-metadata.parquet`仅省去重复prompt数组，原始`requests.parquet`保持不变并在本机保留；两者SHA256均记录。复核/作图提交号与测量提交号分别记录，不向结果目录复制实现代码。无稳定人口的λ明确标注n=0，不画数据点；全部人口模型值及不稳定诊断仍单列。

## 9. 已知局限

写进实验报告的"局限"一节：

1. **合成 token**：最近一轮输出位置的 KV 无法命中，GPU 命中略被低估；用回填模式对照量化
2. **间隔不等于工具耗时**：观察间隔混有用户停顿和并发等待；报告中称为"请求外间隔"
3. **推断链**：链由上游启发式算法拆出，不等于真实 Agent；跨链锚点由原始完成时间推断，只表达单个启动依赖，不还原真实派生和合流依赖
4. **时间压缩**：压缩改变了模型计算时间与间隔的相对比例，只压缩间隔，不压缩模型耗时
5. **缩放**：按根会话缩放改变了不同会话之间的长度比例
6. **固定时长窗口**：长会话在窗口内通常跑不完，会话完成时间（JCT）只能在窗口内完成的会话上统计，会偏向短会话（见第 11 节待定问题）
7. **样本偏差**：AgentX 是经过筛选的 Claude Code 公开样本，不代表所有 Agent 负载
